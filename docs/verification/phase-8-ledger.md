# Phase 8 ledger verification

Phase 8 completed on 2026-09-29. All balance changes now pass through one private posting primitive. It binds actor, operation and idempotency key to a payload hash; locks both balance rows in UUID order; verifies currency; creates a journal and its debit/credit entries in the same transaction; updates projections; and stores the successful result for safe replay. Deferred integrity triggers require at least two balanced entries and reject entries added after the journal-creation transaction.

Synthetic customer funding debits the simulator cash asset and credits the customer deposit liability. Reversal posts the equal-and-opposite journal and retains both records. Owner-safe balance reads derive ledger and available balances from the projection and active unexpired holds. Hold placement locks the balance projection and rejects insufficient available funds. Reconciliation recalculates every projection from immutable entries and reports drift without changing history.

The migration was rehearsed transactionally before application. A real-token test found that the original integrity triggers lacked private-table permission when invoked from a customer command; a separate forward migration converted those two trigger functions to non-callable security-definer functions. After that correction, hosted API tests passed six concurrent identical funding requests with one transaction, competing 75% holds with only one success, idempotency replay and payload mismatch behavior, cross-owner reversal denial, owner reversal, balanced journals and zero reconciliation drift.

The protected account screen now shows ledger and available balances, supports explicit synthetic simulator funding and permits reversal of eligible posted deposits. The provider-backed browser journey posts $125.50, displays it, reverses it and returns to $0.00. Typecheck, lint, 6/6 unit tests, production build, 13/13 public/foundation browser tests, dependency audit and cleanup across 19 resource groups passed. Both hosted targets match at 52 tables, 514 columns, 37 policies and three private buckets with twelve applied migrations and none pending.
